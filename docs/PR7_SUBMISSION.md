# Сдача ПР7 на проекте HomeParty

Основание: «ПР7_Django_SQL.pdf», §5.8, §7.3, §7.5–7.6.
Roomly в методичке — пример: демонстрируем события, участников, задачи,
расходы и пользователей своего проекта. ORM на этом этапе не используется.

## Подготовка

1. Открой HomeParty в VS Code, выбери окружение `.venv`.
2. Для визуального просмотра SQLite открой Extensions (`Ctrl+Shift+X`),
   найди SQLite Viewer и установи подходящее расширение, если его ещё нет.
   Открой `data/homeparty.sqlite`. Это предметная БД; не путай её с `db.sqlite3`.
3. До ручных SQL-экспериментов сделай копию БД через проводник.
4. Из корня HomeParty выполни:

```powershell
.\.venv\Scripts\python.exe -m db.import_json
.\.venv\Scripts\python.exe -X utf8 -m db.check_queries --cli
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe -m pytest -v
.\.venv\Scripts\python.exe -m flake8 . --extend-exclude=venv
git log -5 --oneline
.\.venv\Scripts\python.exe manage.py runserver
```

Импорт повторяемый, но восстанавливает значения JSON для существующих ID.
Ручные изменения БД делай после него и не импортируй повторно для проверки
обновления страницы. Скрипт не удаляет записи, созданные только в SQLite.

## Страницы для показа

| Адрес после `http://127.0.0.1:8000` | Результат |
| --- | --- |
| `/events/` | Все события из SQLite |
| `/events/?min_budget=20000` | Только «Новоселье» с подходящим бюджетом |
| `/tasks/pending/` | Две незавершённые задачи, без «Заказать торт» |
| `/tasks/1/` | Задача и связанное событие из JOIN |
| `/events/ready/` | Форма даты без запроса результатов до ввода даты |
| `/events/ready/?date=2026-10-10` | Корректное сообщение об отсутствии готовых событий |
| `/statistics/` | Счётчики, общие расходы, две группировки, список пользователей |
| `/statistics/?min_tasks=1` | HAVING: нет событий с более чем одной открытой задачей |

Для положительного поиска готовности на копии БД отметь задачи события 1
выполненными: `UPDATE tasks SET completed=1 WHERE event_id=1;`.
После обновления поиска на дату 2026-10-10 появится «День рождения».
Верни исходные значения после показа; не изменяй рабочую БД без копии.

Чтобы показать актуальность данных, на копии временно измени название события
через параметризованный UPDATE или SQLite Viewer, обнови страницу и верни название.
JSON при этом менять не нужно: сайт читает SQLite.

## Ответы и действия по 25 показателям

Порядок соответствует таблице §7.6. В отличие от ПР5–ПР6 вопросы ПР7 выбираются
**выборочно**, а не обязательно подряд. На демонстрацию — не более 5 минут;
опрос заканчивается на первом неправильном или отсутствующем ответе.
Проектная часть — максимум 1,5 балла отдельно от курса; равный вес каждого вопроса
методичкой не указан, не вычисляй его из общей суммы самостоятельно.

| № | Показать | Что ответить / сделать |
| --- | --- | --- |
| 1 | Пять таблиц в SQLite Viewer | events — праздники; participants/tasks/expenses связаны с events; users сохранены как отдельная сущность исходной модели. |
| 2 | `sql/schema.sql` | PRIMARY KEY однозначно определяет запись; FOREIGN KEY запрещает ссылку на несуществующее событие при включённом foreign_keys. |
| 3 | `python -m db.database` | Выполняется схема с IF NOT EXISTS; повтор не удаляет таблицы и данные. |
| 4 | `db/database.py` | connect получает абсолютный DB_PATH; можно показать `PRAGMA database_list;`, чтобы убедиться в пути. |
| 5 | `db/import_json.py` | JSON превращается в кортежи; executemany передаёт значения через ?; родители загружаются раньше дочерних таблиц. |
| 6 | Q07 и исходные JSON | Результат: 2 события, 3 участника, 3 задачи, 3 расхода, 0 пользователей; пустой users.json не заполняем выдуманными данными. |
| 7 | Q01 events_list | SELECT выбирает перечисленные столбцы. Если убрать name, шаблон больше не получит название. |
| 8 | Q03 events_by_budget | WHERE budget >= ?; измени значение в форме и сравни состав событий. |
| 9 | Q04 pending_tasks | completed=0 отбирает задачи в работе, completed=1 — выполненные. |
| 10 | Q05 и Q06 | JOIN связывает task/expense.event_id с events.id; получаем название события вместо голого ID. |
| 11 | Q12 ready_events | Дата должна совпасть и ID не должен входить в подзапрос открытых задач; оба условия обязательны. |
| 12 | Q07 overview | COUNT считает записи; если строк нет, COUNT возвращает 0. COUNT(column) не учитывает NULL. |
| 13 | Q09 tasks_by_event | GROUP BY собирает строки по событию; LEFT JOIN сохраняет и события без задач, COUNT(t.id) даёт для них 0. |
| 14 | Q11 busy_events | WHERE отбирает задачи до группировки, HAVING — готовые группы после COUNT. Измени min_tasks с 0 на 1. |
| 15 | fetch_all и параметры в view | В SQL стоит ?, значение передаётся отдельным кортежем. f-строка с пользовательским вводом создаёт риск SQL-инъекции. |
| 16 | row_factory и fetchall | sqlite3.Row разрешает row['name']; шаблон получает поле по имени, не по числовому индексу. |
| 17 | `/events/` и event_list | Результат Q01 передаётся под ключом events и выводится циклом шаблона. |
| 18 | `/tasks/pending/` | SQL уже исключил выполненные задачи; это не фильтрация скрытием строк в HTML. |
| 19 | `/tasks/1/` | Q14 возвращает поля задачи и event_name/event_date; адаптер сохраняет вложенный контекст шаблона ПР6. |
| 20 | Форма даты | request.GET получает дату, Python проверяет формат, SQLite исполняет Q12 с параметром, шаблон показывает результат. |
| 21 | `/statistics/` | Q07–Q11 дают счётчики, суммы, среднее, минимум/максимум и группы; значения передаются контекстом. |
| 22 | events_list и контекст events | При несовпадении ключа view и имени в шаблоне данные не отобразятся; восстанови одинаковое имя. Демонстрационные правки затем отмени вручную. |
| 23 | Поиск с пустым результатом | fetchall возвращает [], empty показывает сообщение. Ошибка SQL возбуждает исключение, это другое состояние. |
| 24 | SQL на копии БД | Неверное имя столбца даёт OperationalError; неверный JOIN может дать лишние строки без исключения. Проверь поля и ON по schema.sql, исправь и повтори запрос. |
| 25 | Полный путь формы | GET → проверка параметра → сохранённый SQL → sqlite3.Row → context → шаблон → HTML. Проверяй каждый этап, начиная с выбранной БД и параметров. |
