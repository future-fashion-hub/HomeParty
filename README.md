# HomeParty

HomeParty - учебное приложение для организации домашних праздников.

Текущий этап — **ПР7: основы баз данных и SQL**. Веб-страницы получают
данные из `data/homeparty.sqlite` стандартной библиотекой `sqlite3`, без
Django ORM. JSON и консольная версия сохранены для сравнения с ПР1–ПР6.
Порядок подготовки и все 25 вопросов защиты: [ПР7](docs/PR7_SUBMISSION.md).

Проект разрабатывается в рамках практических работ по дисциплине
«Технологии разработки приложений на базе фреймворков».

## Описание проекта

Приложение позволяет планировать домашние события, вести список участников,
контролировать задачи подготовки и учитывать расходы.

В ПР3 проект был переведен на объектно-ориентированную модель. В ПР5 к
существующей консольной версии добавлен веб-интерфейс на Django 5.2. Классы,
JSON-хранилище, тесты и консольная точка запуска сохранены.

В ПР6 весь HTML перенесён в Django Template Language. View-функции
загружают объекты из JSON, подготавливают контекст и вызывают `render()`.
Функция `page()` удалена: HTML-строк во view больше нет.

## Возможности веб-интерфейса

- главная страница с навигацией по разделам;
- список событий и подробная страница события;
- просмотр участников, задач и расходов;
- детальная страница задачи с её событием и статусом;
- динамические URL с числовыми идентификаторами;
- ответы с кодом 404 для отсутствующих объектов;
- адаптивное оформление на Bootstrap 5.3.

## Основные классы

### Event

Класс `Event` представляет событие.

Основные атрибуты:

- `id` - идентификатор события;
- `name` - название;
- `date` - дата;
- `budget` - бюджет.

Основные методы:

- `is_budget_enough()` - проверка, хватает ли бюджета;
- `__str__()` - строковое представление события.

### Participant

Класс `Participant` представляет участника события.

Основные атрибуты:

- `id` - идентификатор;
- `event` - объект `Event`;
- `name` - имя участника.

Основные методы:

- `__str__()` - строковое представление участника.

### Task

Класс `Task` представляет задачу подготовки события.

Основные атрибуты:

- `id` - идентификатор;
- `event` - объект `Event`;
- `title` - название задачи;
- `completed` - признак выполнения.

Основные методы:

- `complete()` - отметить задачу выполненной;
- `__str__()` - строковое представление задачи.

### Expense

Класс `Expense` представляет расход.

Основные атрибуты:

- `id` - идентификатор;
- `event` - объект `Event`;
- `title` - название расхода;
- `amount` - сумма.

Основные методы:

- `__str__()` - строковое представление расхода.

## Взаимодействие объектов

Объекты `Participant`, `Task` и `Expense` связаны с объектом `Event`.

Пример:

```text
Participant -> Event
Task        -> Event
Expense     -> Event
```

В реализации ПР3–ПР6 связи объектов сохранялись в JSON через `event_id`.
Начиная с ПР7 Django-view получают эти связи из SQLite; прежние функции
`storage.py` продолжают использоваться консольной версией.

## Шаблоны и контекст

Общий каркас находится в `templates/base.html`. В настройках указан
`DIRS = [BASE_DIR / "templates"]`, а `APP_DIRS = True` позволяет находить
шаблоны внутри приложений. Каждое приложение содержит каталог
`templates/<имя_приложения>/`.

Все страницы наследуют `base.html` через `extends` и переопределяют
блоки `title` и `content`. Общая навигация подключается через
`include "includes/navigation.html"`.

Повторяемые компоненты:

- `events_app/includes/event_card.html` — карточка события;
- `tasks_app/includes/task_status.html` — статус задачи в списке и деталях.

В ПР6 представления передавали объекты Event, Participant, Task и Expense
через словарь контекста. В ПР7 те же шаблоны получают именованные строки
SQLite и адаптированные JOIN-результаты. Шаблоны перебирают коллекции через `for`,
обрабатывают отсутствие данных через `empty`, показывают состояния через
`if / else`. Если событие или задача отсутствует, сообщение формируется
в том же шаблоне, а `render(..., status=404)` возвращает правильный HTTP-код.
Расчёт бюджета остаётся в Python, вне шаблонов.

Используемые фильтры:

- `length` — количество объектов и открытых задач;
- `default` — подпись при пустом названии или отсутствии даты;
- `floatformat:2` — отображение бюджета и расходов с двумя знаками.

## Общая страница 404 и обновлённые требования ПР5–ПР6

В обновлённой ПР5 добавлен общий обработчик неизвестных адресов.
В `homeparty/urls.py` зарегистрирован
`handler404 = "homepage.views.page_not_found"`. Представление вызывает
`render(request, "404.html", status=404)`; шаблон наследует `base.html`.
Обработчик вызывается при отсутствии маршрута или исключении `Http404`,
но только при `DEBUG = False`. Ответы для отсутствующих событий и задач
сохраняют собственные сообщения и код 404.

Для обычной разработки используется `homeparty.settings` с `DEBUG = True`.
Для локальной демонстрации общей 404 без правки настроек:

```powershell
.\.venv\Scripts\python.exe manage.py check --settings=homeparty.settings_demo
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8001 --settings=homeparty.settings_demo --insecure
```

Откройте `http://127.0.0.1:8001/nonexistent/` или `/events/abc/`.
Настройки демонстрации наследуют `ALLOWED_HOSTS` из основных настроек.
`--insecure` нужен только для локальной раздачи CSS, изображения и JS
при отключённой отладке; для реального размещения сайта он не подходит.

Подробный порядок сдачи, чек-листы курса, команды, маршруты и ответы
на все 25 показателей каждой практической находятся в
[инструкции по сдаче ПР5 и ПР6](docs/SUBMISSION.md).

## ПР7 — реляционное хранение без ORM

`data/homeparty.sqlite` — предметная база, включённая в репозиторий по ТЗ.
Она не связана с `db.sqlite3`, используемой стандартными приложениями Django.
Файл `sql/schema.sql` создаёт таблицы и индексы через `CREATE ... IF NOT EXISTS`.
Связи — «одно событие → много участников/задач/расходов»:

| Таблица | Поля и типы | Ключи и ограничения |
| --- | --- | --- |
| events | id INTEGER, name TEXT, date TEXT, budget REAL | id PRIMARY KEY; все поля обязательны; budget >= 0 |
| users | id INTEGER, name TEXT, email TEXT | id PRIMARY KEY; name обязателен, email может быть NULL |
| participants | id INTEGER, event_id INTEGER, name TEXT | id PRIMARY KEY; event_id → events.id; поля обязательны |
| tasks | id INTEGER, event_id INTEGER, title TEXT, completed INTEGER | id PRIMARY KEY; event_id → events.id; completed IN (0, 1), по умолчанию 0 |
| expenses | id INTEGER, event_id INTEGER, title TEXT, amount REAL | id PRIMARY KEY; event_id → events.id; amount >= 0 |

Даты хранятся как TEXT в формате YYYY-MM-DD, логические значения — INTEGER
0/1. Пользователи остаются независимой сущностью исходной модели; связей,
которых не было в предметной области, не добавлено. Исходный `users.json`
пуст — таблица users корректно содержит 0 записей.

### Подключение, создание и импорт

```powershell
.\.venv\Scripts\python.exe -m db.database
.\.venv\Scripts\python.exe -m db.import_json
.\.venv\Scripts\python.exe -X utf8 -m db.check_queries --cli
```

`db/database.py` задаёт абсолютный путь к БД относительно корня репозитория,
включает `PRAGMA foreign_keys = ON` и `sqlite3.Row`. Соединения закрываются
после получения результатов. `db/import_json.py` сначала загружает events и
users, затем зависимые таблицы; использует `executemany()`, `?`, транзакцию
и `commit()`. Ошибка внешнего ключа откатывает все вставки.

Повторный импорт не создаёт дубликатов: UPSERT обновляет записи с тем же ID.
Записи только из SQLite не удаляются. **Повторный импорт перезапишет ручные
изменения импортированных записей значениями JSON**; не запускайте его при
каждом открытии страницы. JSON-файлы и старые функции `storage.py` не меняются.
Исходный результат: 2 события, 0 пользователей, по 3 участника, задачи и расхода.

CLI из стандартной библиотеки Python 3.12 используется без отдельной установки
sqlite3.exe. Например, открыть консоль:

```powershell
.\.venv\Scripts\python.exe -m sqlite3 data/homeparty.sqlite
```

В ней выполните `SELECT * FROM events;`, `PRAGMA foreign_key_check;`;
выход — `.quit`. `db.check_queries --cli` проверяет все 17 запросов с тестовыми
параметрами и повторяет их в этой CLI. SQLite сама раскрывает параметры для
демонстрации; рабочие запросы всегда выполняются с отдельным списком значений.

### Каталог SQL-запросов и страницы

Запросы хранятся **только в `sql/queries.sql`**, с именем и назначением в
комментарии. Представления вызывают `fetch_all`/`fetch_one`, получая строки
`sqlite3.Row`. Для прежних вложенных шаблонов JOIN-строки адаптируются через
`db/presentation.py`; данные из JSON в веб-части больше не загружаются.

| № / имя | Назначение | Где результат виден |
| --- | --- | --- |
| Q01 events_list | Список, ORDER BY | `/`, `/events/` |
| Q02 users_list | Список, LIMIT и OFFSET | `/statistics/`, раздел пользователей |
| Q03 events_by_budget | WHERE budget >= ? | `/events/?min_budget=20000` |
| Q04 pending_tasks | WHERE completed = 0 | `/tasks/pending/` |
| Q05 tasks_with_events | JOIN задач и событий | `/tasks/` |
| Q06 expenses_with_events | JOIN расходов и событий | `/expenses/` |
| Q07 overview | COUNT по пяти таблицам | `/statistics/` |
| Q08 expense_totals | COUNT/SUM/AVG/MIN/MAX, COALESCE | `/statistics/` |
| Q09 tasks_by_event | GROUP BY, LEFT JOIN | `/statistics/`, задачи по событиям |
| Q10 expenses_by_event | GROUP BY, SUM | `/statistics/`, бюджет по событиям |
| Q11 busy_events | WHERE, GROUP BY, HAVING COUNT > ? | `/statistics/?min_tasks=0` |
| Q12 ready_events | Дата и NOT IN открытых задач | `/events/ready/?date=2026-10-10` |
| Q13 event_detail | Поиск события по ID | `/events/1/` |
| Q14 task_detail | JOIN и поиск задачи | `/tasks/1/` |
| Q15 participants_with_events | JOIN участников и событий | `/participants/` |
| Q16 event_metrics | COUNT и SUM одного события | `/events/1/` |
| Q17 event_pending_tasks | Открытые задачи события | `/events/1/` |

Таким образом, отдельно представлены не менее двух выборок списков (Q01–02),
двух фильтраций WHERE (Q03–04), двух JOIN (Q05–06), двух агрегатных запросов
(Q07–08) и двух группировок (Q09–10). Все 17 запросов используются веб-частью;
это проверяется отдельным тестом покрытия сценариев, а не только наличием SQL.

### Пользовательские сценарии ПР7

Сохранены все страницы ПР6 и добавлены:

- поиск событий по минимальному бюджету на странице «События»;
- страница «Задачи в работе» с SQL-фильтрацией;
- поиск готовых событий на выбранную дату;
- статистика, включая HAVING с пользовательским порогом.

Поиск готовности — адаптация учебного примера поиска свободных помещений:
в HomeParty нет помещений/бронирований, поэтому выбираются события на дату,
не имеющие открытых задач. Это не поиск площадки и не гарантия проведения
праздника. Сейчас обе исходные записи имеют открытые задачи, поэтому поиск
показывает корректный пустой результат. Положительный сценарий проверен
на отдельной временной БД, без изменения исходных данных проекта.

Значения бюджета, даты и порога приходят из GET-форм, проверяются в Python
и передаются SQL через `?`. Некорректный ввод даёт понятное сообщение и код 400;
отсутствующие объекты по-прежнему дают 404. Пустая выборка — нормальный результат,
обрабатываемый `empty`, а не ошибка SQL. Навигация использует именованные URL.

Проверки ПР7: `manage.py check`, `pytest -v`, `flake8 . --extend-exclude=venv`.
В комплект входят SQLite-файл, схема, запросы, импорт и тесты. Следующий этап —
Django ORM; в ПР7 он не используется для предметных данных.
